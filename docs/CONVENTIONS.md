# Правила работы команды

Короткий свод договорённостей. Цель — чтобы 8+ человек могли работать
параллельно и не мешать друг другу.

---

## 1. Git: ветки

```
main      ← только стабильный код, сюда попадаем через PR из develop
  └ develop ← интеграционная ветка, тут собираются все фичи
      └ feature/<тема>  ← рабочая ветка участника (одна задача = одна ветка)
      └ fix/<тема>      ← исправление
      └ chore/<тема>    ← инфраструктура, доки, зависимости
```

Именование: `feature/teachers`, `feature/schedule-api`, `chore/docker-prod`.

```bash
git switch develop
git pull                                   # всегда начинаем с актуального develop
git switch -c feature/teachers
# ... работаем, коммитим ...
git push -u origin feature/teachers        # затем Pull Request в develop
```

Правила:
* **Никогда не коммитим в `main`.** `main` защищён, только через PR.
* Ветка живёт недолго (1–3 дня). Долгая ветка = конфликты.
* Перед PR делаем `git pull --rebase origin develop` — конфликты решает автор ветки.
* Один PR = одна задача из `docs/tasks/`. Не смешиваем фичу и рефакторинг.

## 2. Git: коммиты (Conventional Commits)

```
<тип>: <что сделано>            # до 72 символов, в повелительном наклонении

feat: add GET /api/teachers with filters
test: cover teachers endpoint with bad query params
fix: return 404 for unknown /api routes
docs: describe docker task
chore: bump ruff to 0.6
refactor: move data access to services layer
```

Типы: `feat`, `fix`, `test`, `docs`, `chore`, `refactor`, `ci`.
Полезно указывать задачу: `feat: add schedule endpoint (task 02)`.

## 3. Pull Request и ревью

* Заголовок PR = как у коммита. В описании — `Closes #<номер задачи>`.
* Тело PR заполняем по шаблону `.github/pull_request_template.md`.
* CI обязателен зелёным: `lint` → `test` → `docker`.
* Минимум **1 approve** от другого участника (код читает человек, а не только CI).
* Ревьюер проверяет: контракт API, наличие тестов, docstring, отсутствие секретов.
* Автор не мержит свой PR сам, если найдены замечания. Спорные вопросы — в комментарии к PR.

## 4. Стиль кода

* Python: PEP 8, длина строки 100, типы у аргументов и возврата, docstring **по-русски**.
* Линтер один для всех: `ruff check .` (`make lint`, автофикс — `make format`).
* Импорты: сначала stdlib, потом сторонние, потом свои (`api...`).
* Имена файлов/роутов — по фиче, в единственном числе: `department.py`, не `utils2.py`.
* JS: 2 пробела, `const`/`let`, без глобальных переменных кроме `init<Страница>`.
* CSS: классы в kebab-case, цвета только через переменные из `base.css`.
* Запрещено: логировать секреты, коммитить `.env`, хардкодить пароли и адреса БД.

## 5. Тесты

* Тест пишем **вместе** с фичей (сначала падающий тест — потом код: TDD).
* Тест из одного сценария, имя = утверждение: `test_department_returns_full_contract`.
* Структура AAA: Arrange → Act → Assert, разделяем пустой строкой.
* Проверяем не только happy path, но и ошибки (400/404/403).
* Быстро: все тесты — секунды. Если появилась БД — SQLite в памяти.
* Локально: `make test`. Обязательно убедись, что тест **падает**, если сломать фичу.

## 6. Definition of Done (когда задачу можно закрывать)

- [ ] Задача из `docs/tasks/*.md` выполнена полностью
- [ ] Есть тесты, они падают при поломке фичи
- [ ] `make lint` и `make test` зелёные
- [ ] CI на PR зелёный, есть approve
- [ ] Документация/README обновлены, если менялся контракт API
- [ ] Ветка слита в `develop`, локальная ветка удалена

## 7. Общие договорённости

* Один участник — одна задача из `docs/tasks/`. Задачи не делим «наполовину».
* Непонятно — спрашиваем в чате **до** написания кода, а не после.
* Файлы чужих фич не правим: нужна правка — пишем автору или делаем отдельный PR.
* Общий код (`main.js`, `router.js`, `core/config.py`) меняем минимально и предупреждаем.
